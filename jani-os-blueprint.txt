PART 1 - VISION
================================================================================

THE FIVE PILLARS

1. ORTHOGONAL PERSISTENCE - There are no files and no "save." All state lives
   in a single pool of versioned objects that survives power-off. A running
   program resumes after reboot exactly where it was.

2. ZERO-TRUST HARDWARE - The OS assumes storage and network are hostile and
   the CPU may leak. All objects are encrypted at rest and in flight; boot is
   measured; the design maps onto confidential-computing hardware (SEV-SNP,
   TDX) when available. (Honest scoping: fully homomorphic execution is
   thousands of times too slow for general compute - see Phase 7.)

3. DISTRIBUTED COMPUTE - Many devices, one computer. Running programs can
   pause, migrate to another node, and resume. Objects replicate and merge.

4. SEMANTIC INTELLIGENCE - The kernel indexes what data MEANS. Programs query
   for objects by similarity and description, not by path. Permissions can be
   contextual.

5. INTENT-BASED UI - No apps. The user states an intent; the OS composes
   disposable micro-runtimes on one canvas to fulfill it.

THE EIGHTEEN UPGRADES

Foundational (designed into core data structures from the start):
  U1  Time-travel snapshots      - copy-on-write versioning, system rollback
  U2  Single address space       - one global address map, no per-process
                                   page tables; isolation via capabilities
                                   and the WASM sandbox, not the MMU
  U3  Live hot-swap components   - replace running system parts, no reboots
  U4  Deterministic record/replay- reproduce any session bit-for-bit

Gap-fillers (what Windows, Linux, and macOS miss):
  U5  Sandboxed user-space drivers - a driver crash restarts the driver,
                                     never the machine
  U6  Data provenance ledger     - every object records who created, read,
                                   and modified it; true revocation
  U7  Zero-install rot-free apps - an app is one object; install = copy,
                                   uninstall = delete; no registry/dep hell
  U8  Cryptographic identity     - every user and device is a keypair;
                                   passkey-native; zero passwords anywhere
  U9  Latency-guaranteed UI      - scheduler-enforced input-to-photon budget;
                                   background load can never steal a frame
  U10 Per-component budgets      - metered CPU/memory/energy per component,
                                   user-visible and user-cappable
  U11 Live collaboration         - any object shareable with another identity
                                   and merged in real time (CRDT)
  U12 Causal introspection       - the OS can answer "why is it slow?"
  U13 Disposable ephemeral worlds- fork a snapshot, run untrusted code,
                                   discard with zero residue
  U14 Zero-copy IPC              - components pass object references, never
                                   serialized copies

Later-phase:
  U15 CRDT device sync           - offline-first conflict-free merging
  U16 Accelerator scheduling     - GPU/NPU as first-class scheduled resources
  U17 Declarative system state   - whole machine config as one versioned,
                                   reproducible object
  U18 Post-quantum crypto        - ML-KEM (Kyber) key exchange from day one

CAPABILITY-BASED SECURITY is not on this list because it is not optional: it
is the substrate. Pillars 2, 4, 5 and upgrades U5, U6, U11, U13 all depend on
it. There are no users/groups/ACLs anywhere in this OS; there are only
unforgeable capability handles.

PRIOR ART - STUDY THESE, THEY ARE YOUR TEACHERS

  Phantom OS   - the only shipped orthogonally-persistent general OS; proved
                 the "VM owns all state" design you are using. Study its
                 snapshot approach and its failure modes.
  Twizzler     - modern research OS (UCSC) built around persistent objects
                 for NVM/CXL; study its object model and cross-object links.
  KeyKOS/EROS  - 1980s-90s capability + persistence systems; the EROS papers
                 explain checkpointing a whole system elegantly.
  seL4         - the canonical capability kernel; steal its capability
                 concepts (rights, badges, derivation), skip its formal
                 verification.
  Theseus      - live-evolution OS; study how it structures hot-swappable
                 components ("cells") with typed interfaces.
  Plan 9       - the best attempt at "the network is the computer"; study
                 what per-process namespaces bought them.
  Barrelfish   - multikernel design; relevant when you do distribution.
  Singularity  - Microsoft Research; software-isolated processes = the same
                 bet you are making with WASM instead of the MMU.
  xv6          - not novel, but the cleanest tiny Unix kernel in C; your
                 reference for "how does a working kernel structure this?"

WHAT IS GENUINELY NEW HERE (your contribution, nothing above has all of it):
persistent WASM components + capability provenance + CRDT-native objects +
semantic query syscalls + intent orchestration, in one coherent design.

PART 2 - ARCHITECTURE
================================================================================

THE THREE SUBSTRATES

Everything in this OS is built from exactly three mechanisms. When you design
any feature, first ask which substrate it rides on; if it needs a fourth
mechanism, redesign it.

SUBSTRATE 1: THE PERSISTENT OBJECT STORE
  The universe is a pool of objects. An object is a contiguous blob with a
  header. The header contains, at minimum:
    - a magic number (corruption tripwire)
    - a 128-bit globally unique object ID (random; never reused)
    - a type ID (what schema the payload follows)
    - a version number (monotonic per object)
    - payload size
    - a CRC32C checksum of the payload (x86 has a hardware instruction)
    - a provenance record: the component ID that created it, the component
      ID that last modified it, and a logical timestamp (U6)
    - reference slots or a reference table: the object IDs this object
      points to (objects reference each other by ID, never by raw pointer)
  Objects are immutable-by-version: a write creates a new version via
  copy-on-write. A SNAPSHOT is just a frozen root table pointing at specific
  versions - which is why time-travel (U1), ephemeral worlds (U13), and
  crash consistency are all the same mechanism.

SUBSTRATE 2: CAPABILITIES
  A capability is an unforgeable handle = (object ID, rights bits, badge).
  Rights bits: read, write, execute, grant (may delegate), and later:
  network, spawn. Components hold capability tables; the kernel validates
  every operation against them. Every successful use appends to the target
  object's provenance ledger (U6). Contextual/semantic permissions (Pillar 4)
  are implemented as capability-granting policies, not a parallel system.

SUBSTRATE 3: WASM COMPONENTS
  All programs, services, and (eventually) drivers are WebAssembly modules
  run by an interpreter embedded in the kernel. This is the load-bearing
  trick of the whole OS:
    - The VM owns 100% of a program's state (linear memory + tables) as
      plain bytes -> snapshotting a running program is copying bytes ->
      orthogonal persistence (Pillar 1).
    - Serializable state -> pause here, resume on another machine ->
      migration (Pillar 3).
    - Instances are cheap and sandboxed by construction -> disposable
      micro-runtimes (Pillar 5, U13) and crash-isolated drivers (U5).
    - You never implement hardware user mode (ring 3), ELF loading, or
      per-process page tables. Sandboxing comes from the VM, not the MMU.

DESIGN INVARIANTS (write these on the wall; every phase obeys them)

  I1  SINGLE ADDRESS SPACE (U2). One global page-table hierarchy. The kernel
      and the object space live in it permanently. Nothing is ever mapped
      per-process.
  I2  ZERO-COPY (U14). Components exchange data by passing capabilities to
      objects. The kernel never serializes or copies payloads between
      components. IPC is: validate capability, share reference, notify.
  I3  HANDLES, NEVER NAMES. No component ever refers to anything by path or
      string identity at the syscall boundary. Names are a UI-layer concept
      resolved to capabilities by a naming service.
  I4  CHECKSUM BEFORE SNAPSHOT. No object version enters a snapshot without
      its checksum verified. In C, this is what stops a wild-pointer write
      from becoming permanent.
  I5  EVENT-DRIVEN COMPONENTS. Components are actors: they run
      run-to-completion handlers in response to messages/events, and the VM
      is only ever snapshotted BETWEEN handler invocations. This one decision
      means you never have to capture a native interpreter call stack
      mid-execution - it makes persistence, migration, record/replay, and
      hot-swap each about 10x easier. (Phantom OS needed complex safepoints
      because its threads were long-running; you avoid that entire problem.)
  I6  DETERMINISM AT THE BOUNDARY. All nondeterminism (time, randomness,
      input, network) enters a component only through syscalls. Log the
      syscall results and you can replay the world (U4, U12).

WHAT THE KERNEL ITSELF CONTAINS (the only native-C, trusted parts)
  - boot + CPU setup, interrupts, timers
  - physical/virtual memory management for the single address space
  - the object store engine (versioning, snapshots, WAL, cache)
  - the capability engine
  - the WASM interpreter (vendored WAMR) and its host-function surface
  - the scheduler (with latency classes and metering)
  - a small set of bootstrap drivers (serial, virtio-blk) that later
    re-host as sandboxed components
  Everything else - filesystem-like naming, network protocols, the semantic
  index, the compositor, the intent engine - is a WASM component with
  capabilities. Keep the trusted computing base small.

PART 3 - LANGUAGE STACK AND TOOLCHAIN
================================================================================

LANGUAGES
  - C (C11) for the kernel. Expect 25,000-50,000 hand-written lines total
    across all phases. The kernel is and stays MAJORITY C.
  - Zig is the project's primary language above the C kernel. See THE ZIG
    EXPANSION STRATEGY below - Zig enters as (1) the build toolchain for C,
    (2) the language for native trust-boundary modules called through the
    C ABI, (3) the default language for WASM system components, and (4) the
    official language for desktop/UI components and applications. Zig
    interops with C directly, targets freestanding WebAssembly, and lets
    one pinned toolchain cover the kernel boundary, services, UI, and apps.
  - x86_64 assembly, roughly 200-400 lines TOTAL: the entry stub, interrupt
    entry/exit trampolines, context switch, and a few privileged-register
    helpers. Assembly is only needed where no C ABI exists yet (before a
    stack exists) or where the compiler cannot express the operation
    (swapping stacks, iretq). Even Linux is under 1% assembly.
  - Zig also owns the GUI's visual components in Phase 8: compositor
    decisions, widget-tree rendering, layout, and animation. These compile
    to freestanding WASM like every other component. Graphics helpers use
    Zig vectors, explicit math types, and purpose-built frame arenas;
    native C/Zig host functions handle measured pixel fast paths. Keeping
    this layer in Zig removes a second pre-1.0 toolchain and gives UI code,
    intent parsing, services, and applications one safety model and SDK.
  - WebAssembly as the application ABI. Vendored runtime: WAMR
    (wasm-micro-runtime, Bytecode Alliance) in "interpreter" mode - it is
    written in C, supports bare-metal/no-OS targets through a platform
    abstraction layer you implement, and interpreter mode keeps execution
    deterministic (no JIT), which record/replay needs. Fallback for study:
    wasm3 (smaller, simpler interpreter, also C).
  - Apps: ZIG is the official first-class app language. Applications and
    disposable micro-runtimes compile to the same WASM component ABI as
    system services. C and Rust remain technically possible over that ABI,
    but Jani maintains and documents only the Zig application SDK.

THE ZIG EXPANSION STRATEGY (the kernel stays majority C)

  Zig enters the project four ways, in increasing order of commitment:

  Z1  TOOLCHAIN (from Phase 0): build the C kernel with "zig cc" instead
      of building a GCC cross-compiler.
      - One small download gives you a full C cross-compiler for any
        target (x86_64 freestanding ELF included) - the entire "build a
        cross-GCC" chore in Part 3 disappears.
      - The payoff that matters for Jani OS: in debug builds, zig cc
        compiles C with UndefinedBehaviorSanitizer in TRAP mode by
        default. Signed overflow, null/misaligned dereference, oversized
        shifts, and similar UB in YOUR C code hit an immediate CPU trap
        instead of silently corrupting memory - and your Phase 0
        exception handler reports the faulting instruction address you
        can resolve to file/line. This extends rule R3's sanitizer
        coverage from the hosted twins onto the BARE-METAL kernel
        itself, which plain GCC/clang setups do not give you for free.

  Z2  TRUST-BOUNDARY MODULES (from Phase 2): every module whose job is
      parsing or validating bytes that could be corrupt or hostile is
      written in Zig, compiled to a plain object file exporting C-ABI
      functions, and linked into the kernel. The C kernel calls them
      through an ordinary C header; it cannot tell they are Zig.
      Candidates, phase by phase:
        - Phase 2: WAL record parser, object-header validator (the two
          places where corrupt disk bytes meet kernel memory)
        - Phase 3: WASM module pre-validation, syscall argument decoding
        - Phase 4: capability message decoder
        - Phase 5: ALL network protocol parsers (the most attacked
          surface in any OS) and CRDT merge logic
        - Phase 8: the intent grammar parser
      Why Zig here: compiled in ReleaseSafe mode, Zig keeps runtime
      bounds-checked slices, checked integer arithmetic, checked tagged
      unions, and optionals instead of null pointers - precisely the bug
      classes that turn a parser flaw into persistent-store corruption
      or remote code execution. This is not Rust-grade compile-time
      proof; it is a runtime seatbelt on exactly the code most likely
      to crash the car.

  Z3  SYSTEM COMPONENTS IN ZIG (from Phase 3, the project default):
      WASM is a first-class Zig compile target, so the components/
      directory (drivers, index, compositor, orchestrator) can be
      written in Zig, gaining the same safety checks inside the sandbox.
      New first-party components use Zig unless a vendored C library or a
      measured native fast path gives a concrete reason not to.

  Z4  DESKTOP AND APPLICATION PLATFORM (from Phase 3 onward):
      sdk/zig is the official application SDK. It begins with syscall and
      mailbox wrappers, then grows schema-generated object accessors,
      capability types, CRDT helpers, UI-tree builders, and testing tools.
      Each app is a Zig project compiled to freestanding WASM. In Phase 8,
      the compositor, widget renderer, intent providers, and applications
      all use this same SDK. Performance-sensitive pixel loops become
      native Zig/C host functions only after profiling proves the need.

  RULES OF ENGAGEMENT (so the hybrid stays disciplined):
      - The kernel's core structures and algorithms (object store,
        scheduler, capability engine, memory managers) remain C - Zig
        modules are leaves, never the trunk.
      - Every native Zig module linked into the kernel hides behind a
        hand-written C header. Sandboxed Zig WASM components instead hide
        behind the versioned IDL/component ABI and never link into the
        kernel directly.
      - Pin the Zig version in the repo (a version file + vendored
        tarball note): Zig is pre-1.0 and has breaking releases;
        upgrade deliberately once per phase at most.
      - R3 still applies fully to Zig code: hosted twins, fuzzing,
        property tests. Zig's safe modes catch bugs at runtime in
        production; fuzzing finds them before that.

    intent stage 2 in Phase 8)     math kernels = vendored GGML-class C

  There is no monolithic "OS layer written in language X": above the
  kernel, every service and every piece of the GUI is an independent WASM

  language-neutral for outside ports. Zig's safety checks work identically
  compiled to wasm32, and it is already in the toolchain (Z1). The
  performance upgrade path for any component that needs it is WAMR's AOT
  mode (ahead-of-time
  compilation to native - still deterministic, unlike a JIT), adopted
  per-component without changing its source.

LANGUAGE-LAYER CONTRACTS (what the goals force beyond language choice)

  A polyglot, persistent, hot-swappable OS needs connective tissue that a
  normal OS never does. Three contracts, all born in Phase 3:

  THE IDL - a shared interface & schema language
    A minimal, WIT-inspired interface definition language of your own
    design describes, language-neutrally:
      - object type schemas (fields, sizes, which slots are object refs)
      - component interfaces (the typed messages accepted, versioned -
        what hot-swap compatibility checks compare, U3)
      - the syscall signatures
      - intent-provider manifests (which verbs fulfilled, Phase 8)
      - per-type CRDT merge discipline (Phase 5)
    A host-side tool (tools/idlc) parses .idl files and generates
    accessor/stub code for C and Zig - one schema, one source of truth,
    both supported languages. SCHEMAS ARE THEMSELVES OBJECTS IN THE STORE:
    every type ID in an object header points at a schema object, so the
    system is self-describing - hot-swap checks and semantic queries
    over types both read schemas at runtime. Keep the IDL brutally
    small: records, fixed arrays, slices, enums, object references,
    interface = a list of typed messages. Nothing else until needed.

  COMPONENT SDKs - thin per-language libraries
    sdk/c and sdk/zig embody the actor ABI so every component agrees on
    it: handler export names, mailbox and capability syscall wrappers,
    bounds-checked object accessors
    generated from schemas, CRDT types, and (Phase 8) the widget-tree
    builder. THE PAYLOAD LAW lives here: persistent object payloads
    contain object IDs and offsets, NEVER language pointers - a pointer
    is meaningless after reboot or on another node. The SDK accessors
    make obeying the law easier than breaking it.

  THE DETERMINISM CONTRACT - enforced by the WAMR port
    Replay (U4) and migration (Pillar 3) require a component's execution
    to be a pure function of its message log. The contract:
      - all nondeterminism (time, entropy, input) enters ONLY via
        syscalls (I6), which the recorder logs
      - the WAMR port canonicalizes NaN bit patterns (the WASM spec
        allows nondeterministic NaN payloads; canonicalize them so
        replay is bit-identical across machines)
      - components are single-threaded instances; concurrency is many
        components exchanging messages, never shared-memory threads
    Language tiers under the contract:
      Tier 1 (first-class): Zig, plus C at kernel/native boundaries - no
        runtime; nothing nondeterministic that does not arrive via syscall.
        ZIG IS THE OFFICIAL APP LANGUAGE: one language then spans kernel
        trust boundaries, system services, and apps, and the SDK you already
        maintain covers everything.
      Tier 2 (possible, unsupported): managed-runtime languages (Go,
        C#, ...) can compile to WASM and would even replay correctly -
        their internal randomness is seeded via logged syscalls - but
        their schedulers and GCs fight the run-to-completion handler
        model (I5), and no SDK for them is planned. If one ever exists,
        it is a community port, not your problem.
      Tier 3 (excluded): anything requiring a JIT or OS threads -
        cannot meet the contract.

VENDORED THIRD-PARTY C (code you embed but do not write)
  - WAMR (~50k lines) - the WASM interpreter
  - CRC32C - either the SSE4.2 hardware instruction or a small table
    implementation
  - TweetNaCl or Monocypher (~2-4k lines) - Ed25519 signatures and
    X25519/XChaCha for Phase 5 identity and transport crypto; both are tiny,
    audited, dependency-free C files designed for exactly this
  - ML-KEM (Kyber) reference implementation from pq-crystals (~3k lines) -

CRITICAL COMPILER/ENVIRONMENT FACTS (these will bite you if unknown)
  - The kernel is FREESTANDING: no libc, no startup files. You must provide
    your own memcpy/memset/memmove/strlen etc., because the compiler emits
    calls to them even in freestanding mode.
  - Disable the red zone (a 128-byte stack optimization) in kernel code -
    interrupts corrupt it. There is a compiler flag for this.
  - Disable SSE/AVX/FPU in kernel code initially (kernel-model code flags);
    you enable and manage FPU state deliberately much later.
  - Use the "kernel" code model and higher-half addresses; Limine hands you
    a higher-half direct map (HHDM) of all physical memory - lean on it.
  - Build with your own linker script; Limine's C template provides a
    working one to start from.

THE DEVELOPMENT LOOP (from day one until forever)
  edit -> make -> boot QEMU with serial output to your terminal -> printk
  over serial -> for hard bugs, boot QEMU halted with its gdbstub enabled
  and attach gdb to step through kernel source. QEMU can also snapshot VM
  state, dump memory, and log all interrupts - learn its monitor console
  early; it is your hardware oscilloscope.


================================================================================
PART 4 - C ENGINEERING DISCIPLINE
================================================================================

Why this section exists: in Linux, a wild pointer write crashes a process and
the damage dies at reboot. In Jani OS, all state is persistent - a wild write
can silently poison an object that then gets checksummed... no. Read I4
again: checksum BEFORE snapshot is your immune system, and these rules are
your hygiene. A memory bug here can corrupt your persistent world FOREVER.
This is the tax for choosing C, and it is affordable if you pay it from
day one.

THE RULES

  R1  ASSERT EVERYTHING. Define a kernel assert macro that prints file/line
      over serial and halts. Every function asserts its preconditions; every
      data structure has a "validate" function asserting its invariants.
      Debug builds keep all assertions; release builds keep the cheap ones.

  R2  CHECKSUM EVERY PERSISTENT STRUCTURE. Verify on read, recompute on
      write. Corruption must be detected at the moment of the bug, not
      three snapshots later.

  R3  HOSTED-FIRST DEVELOPMENT. Every allocator, every parser, every data
      structure (object table, capability table, WAL, CRDTs) is written as
      portable C that ALSO compiles on Linux, where you unit-test it under
      AddressSanitizer + UndefinedBehaviorSanitizer and fuzz it with
      libFuzzer. Only code that has survived sanitizers goes into the
      kernel. Keep a tools/ directory with these harnesses forever. This is
      the single highest-leverage rule in this document.

  R4  NO UNCHECKED POINTER ARITHMETIC ACROSS OBJECT BOUNDARIES. All access
      into an object payload goes through bounds-checked accessor functions
      that take (object, offset, length) and assert against the header size.

  R5  MISRA-FLAVORED SUBSET:
      - -Wall -Wextra -Werror from the first commit; add -Wconversion when
        brave
      - all switch statements exhaustive (assert-halt in default)
      - no implicit narrowing conversions in width-sensitive code; use
        fixed-width types (uint64_t etc.) everywhere in the kernel
      - goto permitted ONLY for function-exit cleanup chains
      - all memory ownership documented: every allocating function's comment
        says who frees

  R6  TWO BUILDS ALWAYS: debug (all asserts, no optimization) and release
      (-O2, cheap asserts). Something that only crashes in release is a
      latent UB bug - hunt it immediately with UBSan on the hosted twin.

  R7  COMMIT DISCIPLINE. Small commits at every green state. When (not if)
      you corrupt your development object store, git bisect on the kernel +
      a fresh store image is your recovery path.

  R8  ZIG AT THE TRUST BOUNDARIES. Any code that parses or validates bytes
      the kernel does not fully control - disk records, network frames,
      WASM modules, syscall arguments, user input - is written as a Zig
      module (ReleaseSafe) behind a C header, per the Zig Expansion
      Strategy in Part 3. If you find yourself writing a byte-parsing loop
      in C, stop: that loop belongs in a Zig module. The kernel's trunk
      stays C; the places where hostile bytes enter get the seatbelt.

  R9  MODEL THE TWO DEADLY PROTOCOLS. Before implementing the WAL commit
      protocol (Phase 2) and the replication/sync protocol (Phase 5),
      write a TLA+ (or Alloy) model - a few hundred lines each - and
      model-check the invariants ("no committed version is lost or torn
      after a crash at any step"; "replicas converge"). These are the two
      places where a DESIGN bug, not a code bug, destroys data; testing
      cannot enumerate the interleavings, a model checker can. Models
      live in docs/models/ and get updated when the protocol changes.
      (This is how AWS verifies DynamoDB/S3 protocols - scaled down.)

PART 5 - THE NINE PHASES
================================================================================

Ordering rationale: persistence is the foundation (Phase 2), the WASM layer
makes it programmable (Phase 3), capabilities/scheduling make it safe and
observable (Phase 4), then the OS grows outward: distribution (5), meaning
(6), hardening (7), interface (8). Phases 0-1 are the unavoidable bare-metal
on-ramp. Do not reorder: each phase's milestone is the test harness for the
next.

--------------------------------------------------------------------------------
PHASE 0 - BARE-METAL ON-RAMP                          (~1,500-3,000 lines C)
--------------------------------------------------------------------------------
GOAL: A kernel that boots, prints, and takes interrupts. This phase is pure
learning - nothing Jani-specific yet - and it is where you internalize the
machine.

BUILD, IN ORDER:
  1. Toolchain + Limine C template booting "hello" to the Limine framebuffer
     and to the serial port in QEMU. Serial output is your primary console
     for the entire project; get printk-over-serial (your own minimal
     printf: %s %d %x %p) working immediately.
  2. GDT (Global Descriptor Table) - x86 legacy segmentation setup; in
     64-bit mode it is nearly boilerplate but must exist.
  3. IDT (Interrupt Descriptor Table) + exception handlers for CPU faults
     (divide error, page fault, general protection, double fault). Your
     page-fault handler should print the faulting address (from CR2), the
     instruction pointer, and the error code - this handler is the error
     message for the rest of your career on this project, so make it good.
  4. The interrupt entry/exit assembly trampolines (save registers, call C,
     restore, iretq) - most of your lifetime assembly budget goes here.
  5. Program the legacy PIC (8259) and take timer interrupts from the PIT at
     a fixed frequency; then keyboard interrupts (PS/2) echoing scancodes.
     (Switch to APIC/HPET later, in Phase 4, when SMP or precision matters.)

KEY CONCEPTS TO STUDY: privilege rings, the boot handoff (what state Limine
leaves the CPU in - its protocol spec documents this), interrupt vs
exception vs trap, spurious interrupts.

MILESTONE DEMO: QEMU boots the kernel; it prints over serial; a timer tick
counter increments; keypresses echo; a deliberate null-pointer read produces
a clean page-fault report instead of a triple-fault reboot.

READING: OSDev wiki (Limine Bare Bones, GDT, IDT, Interrupts, 8259 PIC,
Serial Ports); Intel SDM Volume 3 chapters on interrupts (reference, not
bedtime reading); "Operating Systems: Three Easy Pieces" (OSTEP, free
online) Part 1 for concepts.

--------------------------------------------------------------------------------
PHASE 1 - MEMORY AND THE SINGLE ADDRESS SPACE         (~2,000-4,000 lines C)
--------------------------------------------------------------------------------
GOAL: Own all physical memory, own the page tables, and have a kernel heap -
under invariant I1: ONE address space, forever.

BUILD, IN ORDER:
  1. Physical memory manager (PMM): parse Limine's memory map; track free
     4KiB frames with a bitmap (one bit per frame). Simple, debuggable;
     upgrade to a buddy allocator only if profiling ever demands it (YAGNI).
  2. Virtual memory manager (VMM): walk and modify the 4-level x86_64 page
     tables yourself (PML4 -> PDPT -> PD -> PT). Define the permanent
     address-space layout NOW and document it as a memory map in a header
     comment: kernel image region, HHDM region (Limine's direct map of all
     physical memory - use it to access page tables and DMA buffers), a
     kernel heap region, and a vast reserved OBJECT SPACE region where
     Phase 2 will map object versions. No per-process anything, ever (I1).
  3. Kernel heap: a bump allocator first (allocate-only - enough for weeks),
     then a free-list allocator with size classes. kmalloc/kfree/krealloc.
  4. THE HOSTED TWIN (rule R3, established here as a permanent pattern):
     the PMM bitmap logic and the heap allocator compile unchanged on Linux;
     unit tests hammer them under ASan/UBSan; a libFuzzer harness feeds the
     heap random alloc/free/realloc sequences overnight.

ZERO-COPY NOTE (U14): record in your architecture notes that because of I1,
"sending" data between components will never mean copying - Phase 3 makes
this real. The address-space layout you fix here is what makes that possible.

MILESTONE DEMO: allocator test suite passes hosted under sanitizers AND
bare-metal in QEMU; the kernel can map/unmap pages on demand; a page-fault
in an unmapped object-space address is reported with the layout region name.

READING: OSDev wiki (Page Tables, Paging, Memory Map); OSTEP chapters on
address translation and free-space management; study xv6's kalloc.c and
vm.c for shape (it is 32-bit RISC-V xv6 now, but the ideas transfer).

--------------------------------------------------------------------------------
PHASE 2 - THE PERSISTENT OBJECT STORE                 (~4,000-8,000 lines C)
--------------------------------------------------------------------------------
GOAL: The heart of the OS. Objects, versions, snapshots, and crash safety.
After this phase, "the computer forgets things when powered off" stops being
true. Lands: Pillar 1 foundation, U1 (time-travel), U6 (provenance fields),
the U13 primitive (snapshot forking).

DESIGN (in words - your job is to turn this into structs and code):
  - THE OBJECT: header as specified in Part 2, Substrate 1 (magic, 128-bit
    random ID, type, version, size, CRC32C, provenance triple, reference
    table), then payload. Alignment: make headers a fixed power-of-two size.
  - THE OBJECT TABLE: maps object ID -> location of its current version on
    disk and in memory. Start with a sorted array + binary search, hosted-
    tested; a B-tree is the eventual form but do not start there.
  - COPY-ON-WRITE VERSIONING: a write to an object allocates a new payload,
    applies the change, computes the checksum, writes it, THEN atomically
    updates the object table entry. Old versions remain until garbage-
    collected. "Atomically" is the whole trick - see WAL.
  - THE WRITE-AHEAD LOG (WAL): every mutation (new version written, table
    entry updated) is described in a log record written and flushed to disk
    BEFORE the mutation is considered real. On boot, replay incomplete log
    entries. This is the standard database recipe (study SQLite's journal
    documentation - it is the best-written explanation anywhere).
  - SNAPSHOTS (U1): a snapshot is an object table generation - a frozen
    copy-on-write image of the table itself, given its own ID. Rollback =
    make an old generation current. Forking a snapshot to a scratch
    generation and later discarding it is the U13 ephemeral-world primitive.
  - THE CACHE: an in-memory map of hot object versions in the object-space
    region defined in Phase 1, with a dirty list flushed by WAL commit.
  - THE DISK: a virtio-blk driver. Virtio is a simple, well-documented
    paravirtual device standard: you build a descriptor ring in memory,
    the device consumes it. Written in-kernel now; re-hosted as a sandboxed
    component in Phase 4 (U5). Read the virtio spec sections on virtqueues -
    the same mechanism drives networking in Phase 5, so it pays twice.
  - LAYOUT ON DISK: superblock (store identity, current table generation
    pointer) + WAL region + allocation bitmap + object data extents. Keep
    it brutally simple; you are not building ZFS.

PROTOCOL MODEL FIRST (R9): before writing a line of the WAL, model the
commit/recovery protocol in TLA+ and model-check "no committed object
version is lost or torn after a crash at ANY step". A design bug found
here costs an afternoon; found in month three, it costs your store.

ZIG FOCUS (R8, first real use): the WAL record parser and the object-header
validator are the project's first two Zig trust-boundary modules - they are
exactly where corrupt disk bytes meet kernel memory, and bounds-checked
slices plus checked arithmetic are worth far more there than anywhere else.
The store's core logic (table, COW, snapshot bookkeeping) stays C.

C-DISCIPLINE FOCUS: this is the phase where R3 (hosted-first) matters most.
The entire store engine - table, WAL, versioning, snapshot logic - should
run on Linux against a file standing in for the disk, under sanitizers,
with a fuzzer generating random operation sequences interleaved with
simulated crashes (kill the "disk" mid-write, then verify recovery). Only
then wire it to virtio-blk. Crash-consistency bugs are the hardest bugs in
this entire project; find them on Linux where you have a debugger and ASan,
not in QEMU where you have printk.

MILESTONE DEMO: create objects, write versions; kill QEMU mid-write; on
reboot the store recovers to a consistent state with all checksums valid.
Take a snapshot, mutate objects, roll back, show the old state. This demo
is the foundation everything else stands on.

READING: SQLite "Atomic Commit" and "WAL" documentation; the EROS
checkpointing paper ("The Design and Implementation of the EROS
Checkpointing Mechanism"); Twizzler's USENIX ATC paper for the object/ID
design; virtio specification v1.1+ (virtqueue chapters); OSTEP
crash-consistency chapter.

--------------------------------------------------------------------------------
PHASE 3 - THE WASM RUNTIME AS USERSPACE               (~2,000-4,000 lines C
                                                       + WAMR ~50k vendored)
--------------------------------------------------------------------------------
GOAL: Programs. Persistent ones. This phase delivers the single most
important demo of the project. Lands: Pillar 1 completed for programs,
U7 (zero-install apps), U5 begins (driver policy).

BUILD, IN ORDER:
  1. VENDOR WAMR in interpreter mode. Port its platform abstraction layer to
     your kernel: it needs memory allocation (your kmalloc), console output
     (your printk), and stubs for threads/clock you control. No JIT - the
     interpreter is deterministic (I6) and simpler. Per R8, the WASM module
     pre-validation pass and the syscall argument decoder are Zig modules:
     module bytes and syscall arguments are the two untrusted inputs of
     this phase. (Components themselves may be WRITTEN in Zig too - Z3 -
     since wasm32-freestanding is a first-class Zig target.)
  2. THE COMPONENT MODEL (invariant I5 - the most important design decision
     in this document): a component is an event-driven actor. Its WASM
     module exports handler functions (an init handler, a message handler,
     a timer handler). The kernel invokes a handler; it runs to completion
     and returns. Components are NEVER preempted mid-handler and the VM is
     only snapshotted between invocations - so persisting a component means
     persisting its linear memory + its mailbox, never a native call stack.
     Long-running work is structured as chains of self-messages.
  3. COMPONENT STATE AS OBJECTS: a component instance = an object graph
     (module object + linear-memory object(s) + mailbox object + capability
     table object). Because linear memory lives in object-space pages
     (Phase 1 layout), snapshotting a component is just the Phase 2 COW
     mechanism doing its normal job. Nothing special is needed - this is
     the payoff of the whole architecture.
  4. THE SYSCALL SURFACE: host functions exposed to WASM, WASI-shaped but
     capability-based (I3). First set, roughly a dozen calls, described by
     purpose: log a message; allocate a new object (returns a capability);
     read from / write to an object through a capability, bounds-checked
     (R4); send a message + optionally a capability to another component
     (this IS zero-copy IPC, U14: the payload is an object reference);
     receive from mailbox; get logical time; exit. Declare every one of
     these signatures in IDL v1 (see Language-Layer Contracts, Part 3) -
     the IDL's first real use - and this is also the moment sdk/c and
     sdk/zig are born: thin stubs generated from the IDL
     that every later component builds on. Enforce the determinism
     contract in the WAMR port now (NaN canonicalization, no ambient
     entropy) - it is nearly free at this stage and unpayable later.
  5. ZERO-INSTALL (U7): "installing an app" = copying its module object into
     the store. "Running" = instantiating a component from it. "Uninstall" =
     delete the module object; its data objects are findable via provenance
     (U6). No other install state exists anywhere - enforce this by having
     no mechanism for it.
  6. DRIVER POLICY (U5): from now on, new drivers are written as components
     with capabilities to their device's DMA buffers and a kernel-mediated
     interrupt-to-message bridge. (The Phase 2 virtio-blk driver re-hosts in
     Phase 4 as proof.)

MILESTONE DEMO ("the wow demo"): a counter component increments once per
second, printing over serial. Power off QEMU entirely. Boot again. The
counter resumes from exactly where it was - no "save", no "load", nothing.
When this works, you have built the thing that Linux, Windows, and macOS
cannot do. Frame this demo.

READING: WAMR's embedding documentation and platform-port guide (in its
repo); the WebAssembly core spec sections on modules/memories (skim);
the actor model (any Erlang/OTP introduction - your components are actors);
Phantom OS documentation on persistent snapshots (to see the harder road
you avoided via I5).

--------------------------------------------------------------------------------
PHASE 4 - CAPABILITIES, SCHEDULER, REPLAY, HOT-SWAP   (~3,000-6,000 lines C)
--------------------------------------------------------------------------------
GOAL: Make the component world safe, fair, observable, and updatable.
Lands: capability substrate completed, U3 (hot-swap), U4 (record/replay),
U5 proven, U6 enforced, U9 (latency class), U10 (budgets), U12
(introspection).

BUILD, IN ORDER:
  1. CAPABILITY ENGINE: per-component capability tables (array of slots:
     object ID + rights + badge). Syscalls now take capability slot indexes,
     never raw object IDs. Delegation: a component with grant rights can
     send an attenuated capability (fewer rights) in a message. Revocation:
     keep a derivation record so revoking a parent kills descendants
     (seL4's CDT concept, radically simplified). Every validated use
     appends (component ID, operation, logical time) to the object's
     provenance ledger (U6) - ring-buffer it per object to bound growth.
  2. SCHEDULER: components with pending mailbox messages are runnable.
     Round-robin first. Then priorities. Then two Jani-specific classes:
     - INTERACTIVE CLASS (U9): components flagged interactive (input
       handling, later the compositor) get a reserved time budget per
       frame period; the scheduler admits background work only after the
       interactive budget is satisfiable. Design it as budget admission,
       not fancy deadline math.
     - METERING (U10): per-component counters - handler invocations,
       cycles consumed (read the TSC around handler calls), bytes
       allocated, messages sent. Expose via a stats syscall. Energy is
       approximated from cycle counts until real hardware counters exist.
  3. RECORD/REPLAY (U4): thanks to I5 + I6, a component's execution is
     fully determined by its message sequence and syscall results. The
     recorder logs, per component: every delivered message (already
     objects) and every nondeterministic syscall result, with sequence
     numbers. Replay mode re-delivers the same sequence and serves logged
     results instead of live ones - execution reproduces bit-for-bit
     because the interpreter is deterministic. This is also your best
     debugging tool from here on.
  4. CAUSAL INTROSPECTION (U12): the scheduler and allocator emit trace
     events (who ran, who waited on what, who allocated) into a ring-buffer
     object. A stats/query syscall lets a (future) system component answer
     "what consumed the last N seconds?" - the OS explaining itself.
  5. HOT-SWAP (U3): a service's public face is an interface object: a
     versioned binding from a service name to a component instance, its
     message set declared in the IDL - so the upgrade compatibility
     check is a schema comparison, not a prayer.
     Upgrade = instantiate the new module version, wait for the old
     instance to be between handlers (guaranteed possible by I5), move the
     mailbox and relevant state capabilities, atomically repoint the
     interface object. Old code becomes a dead object version - which
     means U1 gives you rollback of a bad upgrade for free.
  6. RE-HOST VIRTIO-BLK as a driver component (U5 proof): the kernel keeps
     only a tiny interrupt-forwarding stub; the driver logic becomes a
     component holding capabilities to the DMA ring objects. Then kill it
     deliberately and watch a supervisor component restart it.

MILESTONE DEMO: two components, one holding a capability the other lacks -
the unauthorized access fails cleanly and appears in the provenance ledger.
A recorded session replays bit-identically (verify by hashing final linear
memories). A running service is hot-swapped to a new version without
dropping its mailbox. The storage driver is killed and recovers with no
kernel panic and no store corruption.

READING: seL4 whitepaper + its capability chapter (concepts only);
Theseus OSDI paper (hot-swap via typed interfaces); "Debugging in the (Very)
Large" and rr-project docs for record/replay framing; KeyKOS "factory"
pattern for supervisor/restart ideas.

--------------------------------------------------------------------------------
PHASE 5 - DISTRIBUTION                                (~4,000-8,000 lines C)
--------------------------------------------------------------------------------
GOAL: Many machines, one object store, migrating programs. Lands: Pillar 3,
U8 (identity), U11 (collaboration), U15 (CRDT sync).

BUILD, IN ORDER:
  1. VIRTIO-NET as a driver component (same virtqueue machinery as Phase 2's
     block driver - this is where that investment pays again). Above it, a
     network-stack component: start with UDP over a minimal IP layer, or
     even raw Ethernet frames between QEMU VMs on a shared bridge - you
     control both ends; you do not need TCP for a long time. R8 applies at
     full strength in this phase: EVERY protocol parser (Ethernet/IP/UDP
     framing, hello messages, replication summaries) and the CRDT merge
     logic are Zig modules - network input is the most attacked surface
     in any OS, and this is the phase where remote bytes first reach your
     kernel's memory.
  2. IDENTITY (U8): every node (and later every user) is an Ed25519 keypair
     (TweetNaCl/Monocypher, vendored). A node's ID is derived from its
     public key. All inter-node messages are signed; sessions establish a
     shared secret via X25519 (upgraded to post-quantum hybrid in Phase 7)
     and encrypt with XChaCha20-Poly1305. There is no password anywhere in
     the OS - identity is cryptographic from the first networked byte.
  3. DISCOVERY + REPLICATION: nodes broadcast signed hello messages on the
     local segment. Object replication: per-object version vectors (a map
     of node ID -> latest version seen) drive an anti-entropy sync protocol
     - periodically exchange "what do you have?" summaries and ship missing
     versions. Study Dynamo's anti-entropy description; yours is a toy
     version of it. Per R9, model this protocol in TLA+ and check
     convergence before implementing.
  4. CRDTs (U15): for concurrently-edited objects, the type's schema
     object (IDL) declares its merge discipline - the type ID points at
     it: last-writer-wins registers (logical timestamps) and
     observed-remove sets first - both are a few hundred lines and fully
     host-testable (R3: fuzz the merge properties - commutativity,
     associativity, idempotence - on Linux). Sequence CRDTs for
     collaborative text are much harder; defer until something needs them.
  5. COLLABORATION (U11): sharing an object with another IDENTITY is the
     same mechanism as syncing with another device - a capability granted
     to a remote identity plus CRDT merge. Live co-editing = both sides
     mutate, anti-entropy converges. No new machinery; that is the point.
  6. MIGRATION (Pillar 3's flagship): pause a component (between handlers,
     I5), sync its object graph (module, memory, mailbox, capabilities that
     make sense remotely) to the target node, instantiate there, forward
     its mailbox binding. To the component, nothing happened.

MILESTONE DEMO: two QEMU VMs on a virtual network. An object edited offline
on both converges identically on reconnect. Two identities co-edit one
object live. The Phase 3 counter component migrates mid-run from VM A to
VM B and keeps counting - the network became the computer.

READING: the Dynamo paper (anti-entropy, version vectors); Shapiro's CRDT
survey ("A comprehensive study of Convergent and Commutative Replicated
Data Types"); local-first software essay (Ink & Switch) for the philosophy;
Monocypher/TweetNaCl docs.

--------------------------------------------------------------------------------
PHASE 6 - THE SEMANTIC LAYER                          (~3,000-5,000 lines C
                                                       + vendored inference)
--------------------------------------------------------------------------------
GOAL: The kernel-adjacent services that understand what data means.
Lands: Pillar 4, U16 (accelerator scheduling, stretch).

BUILD, IN ORDER:
  1. SEMANTIC METADATA: objects gain an optional metadata sidecar object -
     text description, tags, and an embedding vector slot. Producers (and
     later the indexer) fill it.
  2. THE INDEX SERVICE as a component: maintains a mapping from embedding
     vectors to object IDs. Brute-force cosine similarity over a few
     thousand vectors is instant - DO NOT build an ANN index (HNSW) until
     linear scan actually hurts. Host-test the math (R3).
  3. QUERY SYSCALLS (the pillar's public face): "find objects similar to
     this vector/this object's embedding, top K, that my capabilities can
     see." Results are capability-filtered BEFORE return - semantic search
     never becomes a capability-bypass side channel (design this in from
     the first line).
  4. EMBEDDINGS: stage 1 - a trivial-but-real pipeline (normalized bag-of-
     words / TF-IDF vectors) to prove the whole path end-to-end with zero
     ML, written in Zig like the rest of the service. Stage 2 - real
     embeddings, split the compositor way: the ORCHESTRATION (tokenize,
     batch, write metadata) stays a Zig component with no kernel
     privileges, while the MATH KERNELS (quantized matmul - 99% of
     inference time, hopeless in interpreted WASM) are vendored GGML-class
     C compiled native and exposed as accelerator host functions - this is
     BACKEND #0 of the U16 accelerator interface (see step 6). MODEL
     WEIGHTS ARE ORDINARY STORE OBJECTS, not code: they version (roll back
     a bad model, U1), replicate to your other nodes (Phase 5), and are
     provenance-tracked like everything else. Training happens off-device
     on a normal Linux machine; Jani OS only consumes quantized weight
     artifacts - no Python ever runs on Jani OS. CPU-only is fine at hobby
     scale.
  5. CONTEXTUAL PERMISSIONS (Pillar 4's security half): a policy component
     that grants/attenuates capabilities based on declared context (what
     intent is active - wired fully in Phase 8). It is a capability
     FACTORY, not a parallel permission system (Substrate 2 discipline).
  6. ACCELERATOR SCHEDULING (U16): treat an accelerator as a resource
     with a work queue and per-component budget accounting (U10 extended).
     BACKEND #0 is the native CPU SIMD kernel library from step 4 - the
     accelerator interface exists from day one with a software backend
     behind it, so components are written against the interface, never
     the hardware. When a real GPU/NPU driver arrives (post-Phase-8
     hardware work; QEMU limits you until then), it slots behind an
     already-proven interface.

MILESTONE DEMO: store a few dozen text objects; a semantic query syscall for
"birthday party video from Tuesday"-style text returns ranked, capability-
filtered results; a component without the relevant capabilities gets an
empty result for the same query.

READING: sentence-embeddings overview (SBERT docs); GGML repository README
for how small quantized inference works; "vector database" architecture
posts (for concepts - you are building the 1% subset that matters).

--------------------------------------------------------------------------------
PHASE 7 - ZERO-TRUST HARDWARE                         (~2,000-4,000 lines C
                                                       + vendored crypto)
--------------------------------------------------------------------------------
GOAL: Hostile-world hardening. Lands: Pillar 2 (honestly scoped), U18
(post-quantum).

HONEST SCOPING FIRST: fully homomorphic encryption (computing on data the
CPU cannot read) is ~4 orders of magnitude too slow for general compute -
no OS can ship it as the execution model in 2026. The credible version of
Pillar 2, which is what serious industry does: encrypt everything at rest
and in flight, measure the boot chain, minimize trust in storage/network/
peripherals, and map the design onto confidential-computing hardware
(AMD SEV-SNP / Intel TDX) so the HOST (hypervisor/cloud) is untrusted too.
That is what you build.

BUILD, IN ORDER:
  1. ENCRYPTION AT REST: extend the Phase 2 store so object payloads are
     encrypted (XChaCha20-Poly1305 via the vendored library; AES-NI is an
     optimization for later). Keys derive from a store master key via
     per-object subkeys (HKDF-style derivation - a keyed-hash construction,
     also in the vendored library). Design decision to document: checksums
     become authentication tags; the WAL stores ciphertext; the object
     CACHE holds plaintext only in RAM.
  2. KEY HIERARCHY + MEASURED BOOT: master key sealed by a TPM (QEMU +
     swtpm): the TPM releases the key only if boot-chain measurements
     (PCRs) match - a tampered kernel cannot unlock the store. Study TPM2
     PCR sealing; the API is gnarly but the concept is one paragraph.
  3. POST-QUANTUM (U18): upgrade Phase 5 session establishment to HYBRID
     key exchange: X25519 AND ML-KEM-768 (vendored pq-crystals reference),
     hashing both shared secrets together - secure if EITHER survives.
     This is the pattern TLS is adopting; copy it.
  4. UNTRUSTED PERIPHERALS: a threat-model document + enforcement pass:
     DMA-capable devices only ever get capabilities to dedicated buffer
     objects (already true if Phase 3/4 driver discipline held - verify
     it); device-originated data is untrusted input (fuzz the parsers that
     touch it, R3).
  5. CONFIDENTIAL-COMPUTING MAPPING (design document, not code): how Jani OS
     runs as a SEV-SNP/TDX guest - what the attestation report proves to a
     remote party, how remote attestation + U8 identity compose. QEMU can
     emulate some of this; real hardware is a later luxury.

MILESTONE DEMO: raw disk image inspection shows only ciphertext; a bit-flip
in a stored object is detected as an authentication failure on read (not
silent corruption); two nodes establish a hybrid PQ session and sync; with
swtpm, a modified kernel binary fails to unseal the store key.

READING: Monocypher documentation (excellent pedagogy on AEAD/KDF usage);
NIST FIPS 203 overview materials for ML-KEM; AMD SEV-SNP and Intel TDX
whitepapers (skim for the trust model); TPM2 PCR/sealing tutorials.

--------------------------------------------------------------------------------
PHASE 8 - THE INTENT UI                             (~4,000-8,000 lines Zig)
--------------------------------------------------------------------------------
GOAL: The visible revolution - no apps, one canvas, disposable micro-
runtimes. Lands: Pillar 5, U9 visible, U13 completed, U17 (declarative
state).

BUILD, IN ORDER:
  1. COMPOSITOR as a component in the INTERACTIVE scheduling class (U9 pays
     off here), WRITTEN IN ZIG (see the Language Map): owns
     the framebuffer capability; other components render into shared
     surface objects (zero-copy, U14 - a surface is just an object both
     sides hold capabilities to); the compositor blends damage regions per
     frame. Heavy pixel work (blit, blend, fill) goes through native C/Zig
     host functions in the kernel - interpreted WASM is too slow for 60fps
     pixel pushing; the compositor makes the DECISIONS, the host functions
     move the bytes. Keyboard/mouse -> input events -> focused component's
     mailbox.
  2. A WIDGET VOCABULARY, not a toolkit (renderer also Zig): micro-runtimes
     emit declarative UI
     descriptions (a tree of text/list/image/button/input nodes) as
     objects; the compositor renders them. This keeps micro-runtimes tiny
     and makes every surface machine-readable - note that screen-reader
     accessibility falls out of this design for free, which none of the
     big three can claim of their legacy stacks.
  3. INTENT PARSER as a component (its grammar/tokenizer written in Zig
     per R8 - it parses arbitrary user text): stage 1 is a rule grammar (verb +
     object + modifiers) over a registry of INTENT PROVIDERS - components
     declaring, in a manifest object, which verbs they fulfill and which
     capability types they need. Stage 2 (later, optional) is an LLM-backed
     parser component that emits the SAME provider-invocation structure -
     the orchestration below must not care which parser produced the plan.
  4. THE ORCHESTRATOR (Pillar 5's engine): intent -> plan (which providers,
     what data) -> contextual capability grants via the Phase 6 policy
     component (permissions follow the ACTIVE INTENT - the Pillar 4
     security promise, delivered) -> spawn micro-runtime instances ->
     composite their UI trees on one canvas -> tear everything down when
     the intent completes. Micro-runtimes are ordinary Phase 3 components;
     "temporary" just means the orchestrator deletes them afterward.
  5. EPHEMERAL WORLDS (U13 completed): an untrusted intent runs against a
     FORKED SNAPSHOT (the Phase 2 primitive): its micro-runtimes see and
     mutate the fork; on completion the user reviews effects and the
     orchestrator either merges (CRDT machinery, Phase 5) or discards -
     zero residue either way.
  6. DECLARATIVE STATE (U17): one versioned "system manifest" object
     declares which component versions, bindings, and policies constitute
     THIS machine. Boot reconciles reality to the manifest (instantiate
     missing, stop undeclared). Config change = new manifest version; U1
     makes config rollback identical to data rollback. Reproducing your
     whole system on a new machine = syncing one object graph (Phase 5).

MILESTONE DEMO (the project's closing argument): type "note: buy milk
tuesday" - the parser routes to a notes provider; a micro-runtime spawns,
renders on the canvas, stores a semantically-indexed object (Phase 6), and
vanishes. Then run a deliberately hostile intent in an ephemeral world -
it "deletes everything" inside its fork; discard it; show the real system
untouched. Then ask "what did that hostile thing touch?" and answer from
the provenance ledger (U6). No app was installed at any point.

READING: Wayland architecture overview (compositor concepts only - you are
building something far smaller); Ink & Switch essays on malleable/
intent-driven software; Oberon system documentation (the original
"the system IS the interface" OS - closest historical ancestor to
app-less computing).

HAND-WRITTEN CORE CODE PER PHASE (rough, honest ranges)

  Phase 0  On-ramp            1,500 -  3,000
  Phase 1  Memory             2,000 -  4,000
  Phase 2  Object store       4,000 -  8,000
  Phase 3  WASM layer         2,000 -  4,000   (+ WAMR ~50k vendored)
  Phase 4  Caps/sched/replay  3,000 -  6,000
  Phase 5  Distribution       4,000 -  8,000   (+ crypto ~3k vendored)
  Phase 6  Semantic           3,000 -  5,000   (+ inference vendored)
  Phase 7  Zero-trust         2,000 -  4,000   (+ ML-KEM ~3k vendored)
  Phase 8  Intent UI          4,000 -  8,000
  ------------------------------------------------
  TOTAL                     ~25,000 - 50,000 lines of your C and Zig

Those estimates describe the C-heavy kernel and vendored native core, not
the growing application ecosystem. The kernel trunk remains majority C,
while first-party code above it is Zig: trust-boundary modules (R8), system
components, desktop/UI components, and applications. From Phase 3 onward,
expect Zig to become the majority of newly written non-kernel code.

CALIBRATION: xv6, a complete teaching Unix, is ~6k lines. Redox's kernel is
~30k. Linux is ~30 million. This project sits squarely in serious-research-
OS territory - which is exactly why the phase structure exists: every few
thousand lines produces a demo you can show and a foundation the next phase
stands on.

TIME REALISM (solo, learning as you go): Phase 0-1 are commonly a few months
of evenings. Phase 2 is the longest-feeling phase (crash consistency is
subtle) - the hosted-first rule R3 is what makes it survivable. Phase 3
delivers the payoff demo that will recharge you. Expect the full arc to be
a multi-year companion project. That is normal and fine: Linux was "just a
hobby, won't be big and professional" for years too.

WHEN YOU GET STUCK (you will):
  - Reread the relevant xv6 chapter - "how does the simplest working kernel
    do this?" resets your complexity budget.
  - Reproduce the bug on the hosted twin under sanitizers before burning
    days in QEMU.
  - The OSDev wiki + forums and r/osdev have seen every triple-fault you
    will ever cause.
  - Keep a dev log file. Future-you debugging Phase 5 will need to know
    why Phase 2-you chose that WAL format.

SCOPE DEFENSE (the three classic ways this project dies, and the antidotes):
  1. Gold-plating a phase (building the B-tree/HNSW/TCP before anything
     needs it) - the antidote is written into each phase: start with the
     dumb structure, upgrade on evidence.
  2. Skipping the discipline (Part 4) because it feels slow - it is the
     only thing standing between a C typo and a poisoned persistent store.
  3. Reordering phases to reach the exciting parts - each milestone is the
     test harness for the next; Phase 8's demo is only impressive because
     Phases 2-6 are real underneath it.
